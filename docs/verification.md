# 妊婦であることの確認（本人確認）の設計

> **実装状況（このリポジトリ）**
> フロー全体（申請 → 審査 → バッジ → 有効期限で失効）と、下記の「段階的に開ける設計」は実装済み。
> マイナポータル連携（方法A）は**フロー全体を本番と同じ経路で実装済み**で、外部通信だけがモック（`MYNA_MODE=mock`）。実装と申請手続きは [myna-integration.md](./myna-integration.md)。
> 母子健康手帳（方法B）は撮影ガイド・一時保存・審査後の削除まで動く。産院連携（方法C）は未着手。

このアプリの安全性は「参加者が本当に妊婦である」ことに全面的に依存している。ここが崩れると、勧誘・なりすまし・性的な目的の侵入をどれだけ通報機能で受けても追いつかない。**本番公開の前提条件**であり、方式を決めないまま出してはいけない。

---

## 「母子手帳でいいのでは？」への答え：使えるが、そのままでは使えない

母子健康手帳は、市区町村が妊娠届出を受けて交付する公的な文書で、**出産予定日・妊娠週数・交付年月日**が記載されている。妊婦であることの根拠としては筋がいい。

ただし、そのまま「表紙の写真を送ってください」とやると3つ問題が出る。

### 問題1：このアプリの設計と矛盾する

本アプリは **本名・住所を一切保持しない**方針で作ってある（[README](../README.md) 参照）。母子手帳の表紙・見開きには氏名・住所・交付番号が載っているので、写真をそのまま受け取ると、いちばん守りたい情報を自分から集めることになる。しかも妊娠に関する情報は**要配慮個人情報に準じる扱いが必要**で、漏洩したときの damage が桁違いに大きい。

### 問題2：母子手帳は「医師の証明書」ではない

妊娠届出に医療機関の証明書は不要で、届出書に妊娠週数・分娩予定日・受診先を自己申告すれば交付される。つまり母子手帳は**自治体が受け付けた記録**であって、医学的な証明ではない。偽造・借用に対して思ったほど強くない。

### 問題3：期限がない

母子手帳は出産後も乳幼児期を通じて使う。「手帳を持っている＝いま妊娠中」ではない。一度認証したら永続、という設計にすると、**産後2年の人が妊婦として滞在し続ける**ことになる。

## 方式の比較

| 方式 | 確度 | 全国カバー | ユーザー負担 | 集めてしまう個人情報 | 実装コスト |
|---|---|---|---|---|---|
| **A. マイナポータル自己情報取得API（妊婦健診情報）** | **高** | **△ PMH対応自治体のみ** | 低（同意して連携するだけ） | 少（APIの戻り値のみ） | 高 |
| **B. 母子手帳の限定ページ提出＋目視審査** | 中 | ○ | 中（撮影して送る） | **多（マスキング運用に依存）** | 中 |
| C. 産院・クリニック連携（発行コード） | 高 | × 提携先のみ | 低 | 少 | 高（営業が要る） |
| D. 妊婦健診受診票／補助券の提出 | 中 | ○ | 中 | 多 | 中 |
| E. 自己申告のみ（現状） | 低 | ○ | なし | なし | 済 |

### A. マイナポータル連携が本命

**マイナポータルの自己情報取得APIで、自治体が持つ妊婦健診の情報（妊婦健診一覧・健診結果・受診券情報）を取得できる。民間事業者も利用できる。**

- 本人がマイナポータル上で同意して連携するので、**画像を受け取らずに済む**＝氏名・住所を集めなくていい。問題1が消える。
- 自治体の記録が直接返るので、確度が高い。健診の日付が入るので「いま妊娠中」も判定できる。問題3も消える。
- **制約：母子保健（妊婦健診）情報連携に対応した PMH 事業実施自治体に在籍している必要がある。** 全国は当面カバーできない。

→ したがって **A を第一候補にしつつ、対応外の自治体向けに B を用意する二本立て**が現実解。

### B. 母子手帳を使うなら、こう設計する

「表紙を送ってください」ではなく、**必要な情報だけを、必要な期間だけ**受け取る。

1. **提出するのは「出産予定日が記載されたページ」1枚のみ。** 氏名・住所・交付番号は**紙やスマホのマスキング機能で隠してから**撮るよう、アプリ側でガイド（撮影画面に隠す位置を図示する）。
2. **画像はオブジェクトストレージに保存しない。** 審査キューに一時保持し、**審査完了と同時に削除**。DB に残すのは `verifiedAt` / `dueDateVerified` / `method` の3つだけ。
3. **審査は人が目視。** 自動OCRは誤判定が事故に直結するので初期は入れない。数十件/日なら人力で回る。
4. **有効期限を持たせる。** 出産予定日＋8週で認証を失効させ、産後モードへ移行させる（[roadmap.md](./roadmap.md) の「在籍10か月問題」と同じ導線に乗る）。
5. **提出前に何を集めるか明示し、同意を取る。** 要配慮個人情報に準じる扱いとして、利用目的・保存期間・削除タイミングを画面に書く。

### C. 産院連携は「あとで効く」

提携した産院で妊婦健診時にコードを渡してもらう方式。確度が高くユーザー負担も小さいが、提携営業が要るので初期には回らない。**ただし B2B2C の営業（[roadmap.md](./roadmap.md)）と訪問先が同じ**なので、そちらを進める過程で自然に足せる。

## 段階的に開けるという設計（重要）

「認証しないと使えない」にすると、登録の入り口で人が消える。マッチングは人がいないと価値が出ないので、これは致命的。

**認証を利用の条件にせず、「できることの範囲」にする。**

| | 未認証 | 認証済み |
|---|---|---|
| プロフィール閲覧・いいね | ○ | ○ |
| トーク | ○ | ○ |
| **通話** | **×** | ○ |
| プロフィールのバッジ | なし | 「妊婦確認済み」 |
| **「認証済みの人としかマッチしない」設定** | 選べない | **選べる** |

こうすると、

- 入り口は軽いまま保てる
- 慎重なユーザーは「認証済みのみ」に絞って自衛できる → **認証されていないと相手にされない**ので、認証する動機が自然に生まれる
- 音声（証拠が残らずモデレーションが効かない）を認証済みに限定でき、いちばん危ない面を閉じられる

「全員に強制する」より、この非対称な設計のほうが、実際の安全性は高くなる。

## データモデル（実装済み）

`prisma/schema.prisma` の `User` に確認の状態を持ち、審査は `VerificationRequest` のキューで回す。実装は `src/lib/verification.ts`。

| フィールド | 用途 |
|---|---|
| `verificationStatus` | `none` / `pending` / `verified` / `expired` / `rejected` |
| `verificationMethod` | `myna` / `boshi_techo` / `clinic` |
| `verifiedAt` / `verificationExpiresAt` | 確認日と、出産予定日+8週の失効日 |
| `requireVerifiedMatch` | 確認済みの相手としかマッチしない設定 |
| `VerificationRequest.evidenceRef` | 一時ファイルへの参照。**判定時に null にし、実体も削除する** |

失効は読み取りのたびに遅延評価している（`expireStaleVerifications`）ので、バッチを持たなくても期限切れが放置されない。

### 絞り込みは必ず双方向に効かせる

`verifiedGateAllows(me, other)` で、**どちらかが「確認済みのみ」をオンにしていれば双方の一覧から相互に消す。** 片側だけに効かせると「いいねしたのに相手からは見えない」という壊れた状態が生まれるため。おすすめ一覧・いいね一覧・プロフィール詳細・いいね送信のすべてで同じ関数を通している。

## まとめ

- 母子手帳は**使える。ただし「表紙の写真」ではなく「予定日のページだけ・マスキング前提・審査後に削除」**という形に落とすこと。
- 本命は**マイナポータルの自己情報取得API**（妊婦健診情報）。画像を受け取らずに済み、確度も高い。対応自治体が限られるので母子手帳方式と併用する。
- **認証を必須にしない。** 通話と「認証済みのみでマッチ」を認証済みの特典にすることで、入り口を狭めずに安全性を上げる。
- 認証には**有効期限**を持たせ、産後モードへ自然に移行させる。

## 残っている課題

1. **マイナポータル自己情報取得APIの本番接続** — 実装は済んでいるので、残るのは利用申請（仕様書取得 → 事前打合せ → 審査 → 接続試験）と、仕様書に沿った項目名の差し替え。取得できるのは PMH 事業実施自治体に在籍する利用者のみなので、カバー率の把握も要る。→ [myna-integration.md](./myna-integration.md)
2. **産院連携（方法C）** — B2B2C の営業と訪問先が同じなので、そちらと合わせて進める。
3. **審査の運用** — 現状は `ADMIN_EMAILS` に列挙したアカウントが画面から判定するだけ。件数が増えたら、担当者の権限管理と判定ログが必要。
4. **画像の保存先** — プロトタイプではローカルの `.verification-tmp/` に置いている。複数インスタンス構成にするなら、短命な署名付きURLを使うオブジェクトストレージ（ライフサイクルルールで自動失効）へ移す。
5. **再申請の回数制限** — 現状は無制限。総当たりでの突破を防ぐため、回数と間隔の制限を入れる。
